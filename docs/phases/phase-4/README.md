# Phase 4 — Platform layer (router centerpiece)

**Status:** Scaffolding in progress — gateway/tenant/registry/router + fake-worker tests  
**Acceptance:** [ACCEPTANCE.md](ACCEPTANCE.md) · **TDD:** [`docs/testing/phase-4.tdd.md`](../../testing/phase-4.tdd.md)  
**Hardware:** Laptop for API; Colab for GPU-backed integration tests  
**Scope boundary:** implement only the thin gateway, routing, and observability path needed for
Phases 5 and 5.5. No multi-node, RDMA, or production autoscaler is implied by this phase.

## Components

| Component | Path | MVP depth |
| --- | --- | --- |
| FastAPI OpenAI-compatible gateway | `platform/gateway` | `/v1/chat/completions` + streaming |
| Tenant manager | `platform/tenant` | API keys, RPM quota |
| Model registry | `platform/registry` | YAML → registry objects |
| Observability | `platform/observability` | Prometheus metrics + OTEL hooks |
| Autoscaling | `platform/autoscaling` | Queue-depth metric; KEDA YAML sketch |
| **Router** | `platform/router` | **Round robin vs prefix-aware** |

## Steps

### 4.1 Gateway skeleton
- Implement `POST /v1/chat/completions` with OpenAI-compatible request and streaming response shapes.
- Reject invalid input at the HTTP boundary and return a documented error shape.
- Verify with one local fake-worker integration test before connecting a GPU worker.

### 4.2 Tenant + keys
- Read a small YAML tenant registry; authenticate one API-key format.
- Enforce the configured request-rate limit through a shared or platform-native limiter when deployed;
  do not present a process-local counter as production-safe.
- Record tenant id in request logs and metrics without logging secrets.

### 4.3 Registry
- Parse model/worker configuration into a registry that can resolve an eligible worker.
- Keep worker details independent from tenant policy; tenants select allowed models, not worker internals.

### 4.4 Worker client (vLLM OpenAI server)
- Call the pinned Phase 3 vLLM OpenAI-compatible endpoint through a narrow client.
- Preserve streaming, request id, model name, TTFT, completion duration, and error status.
- Validate against the pinned vLLM version; the current repository does not contain a running worker.

### 4.5 Router strategies (disproportionate effort)
- Implement round robin and least-load as baselines before prefix-aware routing.
- Let prefix-aware routing use observed local cache/prefix state, with a deterministic fallback when
  state is unknown or stale.
- Emit the reason for every route choice so Phase 5 can explain both wins and losses.

### 4.6 Metrics export for dashboard (5.5)
- Export route decision, replica id, queue depth, cache hit/miss signal, TTFT, tokens/s, and outcome.
- Wire metrics from the request/worker path; synthetic dashboard-only events do not satisfy Phase 5.5.
- Treat cache state reported by a worker as local to that worker unless a later design explicitly
  introduces a distributed cache index.

## Exit criteria

- A local client can stream one request through the gateway to a real or explicitly labeled fake worker.
- All three routing strategies produce inspectable route-decision events.
- The dashboard-facing metrics are generated by the same request path used for Phase 5.
- The implementation remains a single-node/laptop-first MVP; deployment and autoscaling artifacts are
  planning material until backed by a run.

## Novel piece

Only the **prefix-aware router** needs to be "yours." Everything else should be thin and boring.
